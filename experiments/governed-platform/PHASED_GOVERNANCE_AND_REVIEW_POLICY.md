# Phased Governance and Review Policy

Status: **TESTING-PHASE GOVERNANCE CONTRACT**

## 1. Phase branches

Long-lived phase branches:

- `main` — development/integration source.
- `phase/testing` — falsification and experimental qualification.
- `phase/release` — release qualification only.
- `phase/production` — production qualification and deployment-authority boundary only.

Promotion is one-way and exact-SHA bound:

`main → phase/testing → phase/release → phase/production`

A phase branch is not continuously synchronized from upstream. A promotion must identify the exact source branch, exact source SHA, qualification evidence, decision, and timestamp. Any later source change requires a new promotion candidate.

## 2. Testing phase

Testing is the current active phase.

Rules:

1. Code is written to **release-level engineering quality** even though the phase is testing.
2. External API calls are **off by default**.
3. API calls are allowed only when the API boundary itself is under test or when the user explicitly approves the API/review step.
4. Reviews are **manual by default**.
5. Before review, the assistant/platform must tell the user that review is recommended/required and ask before initiating it.
6. A testing review packet must explicitly state that the task is testing/falsification, not production-readiness assessment.
7. Reviewer focus is the frozen testing contract, correctness, false-green risk, crash/concurrency/recovery/security behavior, test quality, and regressions.
8. Production-only gaps that do not violate the testing contract are not testing blockers. They are classified `DEFERRED_TO_RELEASE` or `DEFERRED_TO_PRODUCTION`.
9. Reviewer PASS/BOUNDED_PASS/consensus is evidence, never automatic authority.
10. Raw reviewer findings do not become governance requirements automatically. They must be adjudicated.
11. Material findings should be converted into executable falsification tests before repair where practical.
12. Red-first evidence, failure preservation, exact candidate SHA, deterministic adjudication, and regression requalification remain mandatory.

### Testing pass meaning

`TESTING_BOUNDED_PASS` for a slice/component requires:

- frozen contract satisfied;
- required acceptance cases pass;
- standard adversarial matrix exercised;
- relevant earlier regressions pass;
- every observed failure root-classified;
- no unresolved material code/test/fixture/requirement defect;
- review performed when testing policy calls for it and the user approves it;
- reviewer findings adjudicated rather than copied into policy;
- material valid findings falsified where practical;
- exact candidate SHA requalified after the last repair;
- explicit untested/deferred risks recorded.

Overall testing-phase pass additionally requires the complete intended release scope to satisfy bounded testing, integrated regressions to pass, and no unresolved material testing blockers.

Testing pass means **ready to begin release qualification**. It does not mean production ready.

## 3. Release phase

`phase/release` receives only an exact testing-qualified SHA.

Release rules become stronger and may include:

- feature freeze except release-blocker fixes;
- full integrated/end-to-end qualification;
- real API integrations where the relevant boundary is mature enough;
- configuration/environment validation;
- migration/upgrade/recovery tests;
- performance and resource-limit qualification;
- security/secret handling qualification;
- release artifact reproducibility and exact-SHA binding;
- review appropriate to release qualification;
- any code change invalidates prior release qualification.

Release pass means ready to begin production qualification, not production deployed.

## 4. Production phase

`phase/production` receives only an exact release-qualified SHA.

Production qualification may require:

- authenticated reviewer/provenance requirements;
- production credential/IAM/secret-manager validation;
- real provider/environment identity;
- deployment authorization and terminal authority;
- rollout and rollback gates;
- production telemetry and audit evidence;
- environment-specific health checks and operational controls;
- signed/reproducible artifacts where required.

Manual review alone must never establish production qualification.

## 5. Review request contract

Every review request generated by the phase-aware testing/release/production wrapper must include:

- `phase`;
- `phase_branch`;
- `review_scope`;
- `required_dimensions`;
- `explicit_nonclaims`;
- `out_of_scope_dimensions`;
- `allowed_evidence`;
- `review_transport_policy`;
- `reviewer_instruction`;
- `promotion_target`.

Testing packets must say explicitly:

> This is a TESTING/FALSIFICATION review of release-quality code, not a production-readiness review.

Reviewers may surface future risks, but an out-of-phase finding that does not violate the current frozen contract must be deferred rather than treated as a blocker.

## 6. Finding adjudication

Reviewer findings follow this path:

`finding → evidence check → falsification where practical → root-cause classification → valid / invalid / unresolved → repair if valid → regression preservation → generalize into durable governance only when justified`

Raw findings never flow directly into later-phase governance as truth.

Valid generalizable lessons flow forward as adjudicated evidence and permanent tests/rules. Release or production discoveries that reveal an earlier testing weakness should also flow backward into future testing coverage without rewriting historical results.

## 7. Production-strength review protocol remains intact

The existing authenticated production review protocol is not weakened or deleted by this policy. The phase-aware layer determines which review contract applies to the current phase. Production qualification continues to use the stronger provenance/authority requirements.
