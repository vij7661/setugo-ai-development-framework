D. HIGH_FINDINGS
1. Missing exact per-candidate reviewed-file allowlist. The file-selection policy selects governance-runtime/*.py by diff against the Slice7 base and path globs, not by an exact reviewed path+blob manifest from the source indexes. This can import candidate-commit files that are not slice-owned reviewed evidence. The hard-fail check only confirms selected blob equals the roster candidate blob; it does not confirm the path was authorized for that slice. Remediation: require exact per-candidate path+blob manifests, hard-fail on any unlisted selected path, and hard-fail if the materialization source commit is not exactly the roster candidate.

2. Integration acceptance false-green risk. The proposal does not hard-fail on skipped, xfailed, uncollected, or conditionally bypassed tests. Reviewed acceptance suites designed for sibling branches may skip when dependencies are absent or branch-specific markers do not match. A green run could therefore fail to exercise imported reviewed behavior. Remediation: add an integration-specific oracle requiring no skips/xfails/not-collected for imported slice tests, exact test collection, assertion of imported module identities, and prohibition of test-time monkeypatching that changes semantics.

3. Integration-only harness/workflow can silently create dependency or authority semantics. The proposal permits new integration-only manifest/harness/workflow files that do not alter imported reviewed modules, but it does not constrain those files to declarative import/test invocation. Such files could monkeypatch, wire cross-slice dependencies, or execute semantic selection, currentness, qualification, evidence-promotion, or other authority-bearing logic before Stage 2. Remediation: require integration-only harness/workflow code to be declarative-only, prohibit semantic branching beyond test invocation, prohibit monkeypatching/cross-slice semantic wiring, and bind exact harness/workflow blobs into the fresh independent review.

4. Rejected predecessor and unreviewed descendant exclusion is not mechanically fail-closed. The roster rule is textual. Hard-fail conditions do not require verifying that the materialization source commit is exactly a roster candidate, that candidate ancestry excludes rejected S20-S22 predecessors, or that selected blobs are not inherited from rejected predecessor trees unless explicitly re-reviewed. A descendant with identical selected blobs could source bytes and extra files. Remediation: hard-fail on source-commit mismatch, rejected ancestry, or selected blob matching a rejected predecessor for the same path without explicit re-review.
